# Security review and operating boundary

Grimarr is a single-owner manager for a trusted private network. Authenticated owners can configure internal service URLs and storage roots; those controls are administrator capabilities. Keep the service on loopback or a trusted private network, or provide HTTPS through a correctly configured deployment. Cookies are HttpOnly and SameSite Strict, and Secure when the request is HTTPS. HTTP is retained for existing private-network deployments. No permissive CORS policy is enabled.

## Reviewed controls

- Every owner API requires authentication. Mutating requests also require the `X-Grimarr` header. Login is limited globally to five attempts per minute for the single owner; authenticated catalog lookups have a separate quota that anonymous requests cannot consume.
- Passwords have no length/composition restrictions. The private `owner-password.json` file stores a salted PBKDF2-HMAC-SHA256 verifier (600,000 iterations, random 32-byte salt), never the plaintext. Legacy `GRIMARR_PASSWORD` initializes a missing file only; remove it from the deployment afterward. The interactive `password` command updates the hash atomically with Unix mode `0600`; see [PASSWORDS.md](PASSWORDS.md). No password/hash is exposed by APIs or logged.
- Session cookies contain an encrypted random session-version claim, checked on every authenticated request. The nonce and fingerprint of the salted verifier are stored in a protected, atomically replaced config file. Updating the password file rotates the nonce and invalidates prior cookies immediately, including when reusing a password; no restart is needed. Same-password restarts retain valid sessions. The hash-storage migration requires signing in again. Logout clears the browser cookie; changing the password revokes a stolen cookie. Hashes are one-way and cannot recover a forgotten password; config operators can reset it.
- API bodies default to 64 KiB; Quick Add and its preview permit up to 24 MiB of JSON for a validated torrent file up to 16 MiB. Both content-length and streamed requests are bounded. Integration/catalog responses and streamed downloads are bounded. Prowlarr torrent downloads have a timeout covering the entire body, not only response headers.
- Integration redirects are not followed. Prowlarr credentials are attached only to the configured proxy origin and base path. External release download URLs are rejected. Internal service URLs remain intentionally configurable by the authenticated owner.
- All submitted magnets require one v1 identity and reject literal control characters or extra URL lines. Torrent files from both Quick Add and Prowlarr receive structural/path/piece validation; torrent symlink entries are rejected before submission.
- Audio probes accept only local files and supported audio containers. Playlists and network protocols are disabled. Probes have a timeout, use argument lists without a shell, and do not publish invalid imports. Import paths reject traversal and symlinks, including dangling symlinks. Download/config directories must have trusted writers: path checks do not constitute an OS sandbox against a malicious local process racing filesystem changes.
- Passwords are not returned by APIs. Connection secrets, private URLs/magnets, torrent payloads, selected release identifiers, and failed-release identifiers are protected with ASP.NET Data Protection. Identifiers are protected because indexers can use credential-bearing URLs as IDs. Public projections omit these private fields. Routine HTTP diagnostics do not log request query strings, and errors avoid raw integration URLs/bodies.
- Existing private identifiers are migrated in place without altering book identities or workflow states. The migration rewrites protected fields, vacuums old database pages, and truncates the WAL before marking completion. SQLite secure deletion is enabled for subsequent writes. An interrupted migration is retried on the next startup. Operator backups may contain pre-migration plaintext identifiers and must remain private.
- New Unix config roots are created with mode `0700`. Existing operator-managed permissions are retained. The entire config directory, encryption keys, database, WAL, and backups must be accessible only to trusted operators. Encryption does not protect against someone who can also read the protection keys. The container runs as a non-root user; the supplied Compose file drops capabilities and prevents privilege escalation.
- Text from providers and books is rendered as text, not injected HTML. Apple descriptions are stripped of markup. Artwork and store links use fixed trusted host rules; server-downloaded artwork is bounded and restricted to JPEG/PNG. A restrictive CSP, no-sniff, no-referrer, frame blocking, and disabled camera/microphone/geolocation policies are sent. Configuration is not served by the static file handler.

## Dependency and build checks

The frontend uses a small esbuild script plus TypeScript checks. Vite and its plugin chain were removed because a transitive picomatch ReDoS advisory had no patched published release, including in current Vite versions. No vulnerable dependency version is hidden behind an audit exception or unsafe downgrade. `npm ci --ignore-scripts` installs the locked dependency graph; builds and CI audit development and production dependencies. The production image contains static frontend output, not a Node development server. `npm run dev` watches local files and copies output to the running backend; refresh the browser to load changes.

NuGet direct/transitive versions and content hashes are recorded in `src/Grimarr/packages.lock.json`. Container restores use locked mode; vulnerability warnings fail restores. CI also runs dependency audits and targeted security integration tests. Audit results describe the available advisory feeds at review time and must be rerun as dependencies and advisories change.

The deployed `945e1b0` runtime uses the official .NET 10 Ubuntu 26.04 base with available OS package upgrades applied. The unused bundled Pebble supervisor was removed. On 2026-11-23, npm and NuGet audits reported no known vulnerable dependencies. An isolated Trivy image scan reported no critical/high vulnerabilities or embedded secrets, but retained 364 medium and 12 low OS package findings across 99 unique CVEs, with no fixed versions reported. These lower-severity findings remain open and require ongoing vendor/advisory monitoring. They are not suppressed or treated as resolved. See the step 5 results in [RELEASE_STATUS.md](RELEASE_STATUS.md).

## Upgrading and rolling back this security change

Back up the **entire config directory, including protection keys**, while the app is stopped, and retain the original image and Compose file. This change encrypts fields that older binaries do not decode. To roll back to an older binary, restore its corresponding complete pre-upgrade config backup before starting it; changing only the image is insufficient. Keep backups private and do not commit them, `.env`, or protection keys.

The application/dependency review and regression tests are documented in [RELEASE_STATUS.md](RELEASE_STATUS.md). They are not an independent penetration test or a guarantee against future vulnerabilities. Baseline installation/upgrade/full-config restore checks and candidate packaging are completed in steps 6–7; public CI, broader beta/storage coverage and stable/public promotion remain outstanding. Release archives are unsigned, include checksums/source/inventory/scan results, and do not establish signed publisher identity; see [RELEASE.md](RELEASE.md). [BACKUP_AND_RESTORE.md](BACKUP_AND_RESTORE.md) explains the verified config archive tool and its scope. Startup validates decryptable config before health; missing protection keys, corrupt session state and existing protection state without its database require a complete matching restore.
